# xLLM 模型分析优化

## 确定模式与权限

以本次用户输入判断模式，不因仓库文件、历史对话或本 Skill 自身出现相关词语而触发：

- 用户肯定地要求“深度分析”“深入分析”“全面深挖”或语义等价内容时，设置 `deep_analysis=true`。
- “不需要深度分析”“先不要深入”等否定表达设置 `deep_analysis=false`。
- 未出现肯定的深挖请求时，默认 `deep_analysis=false`，完成基础阶段后停止。

区分交付权限：

- 用户只要求分析、审查或方案时，只读代码和可用产物，输出结论与后续步骤，不修改生产代码。
- 用户明确要求优化、修改、实现或替换时，才实施改动；每次只验证一个主要假设。
- `deep_analysis=true` 只扩大分析深度，不自动授权代码修改、安装依赖或执行高成本外部任务。

## 建立分析契约

1. 定位 xLLM 仓库和目标模型，读取所有适用的 `AGENTS.md`、代码规范和构建说明。
2. 记录模型版本、PREFILL/DECODE 阶段、batch/并发、输入输出长度、dtype/量化、设备和 Rank 数、TP/PP/EP/DP 拓扑、Graph/Stream 设置以及目标指标。
3. 还原从模型入口到 Layer、Kernel、内存操作和 Collective 的真实调用链；同时标记 Shape、Layout、生命周期、原地修改、别名和跨 Rank 依赖。
4. 固定需要保持的支持范围和正确性标准。修改工作需要先建立覆盖目标路径的 Reference、测试和可重复基线；具体要求见 [correctness-and-validation.md](references/correctness-and-validation.md)。
5. 如果关键工作负载或并行配置无法从输入、代码或现有配置推导，且不同选择会实质改变结论，只询问这个必要信息。

## 基础阶段：每次都执行

完整读取 [basic-analysis.md](references/basic-analysis.md)，按证据检查以下核心方向：

1. 重复计算，以及能在正确生命周期和失效条件下复用的结果；
2. 无消费者的返回值、中间结果和不必要的数据处理；
3. 可批量化、向量化或合并执行的循环展开代码；
4. 不必要的 Host/Device、跨设备或跨 Rank 拷贝，以及阻塞同步；
5. 集合通信的语义和通信量是否合理，是否存在通信量更小且更易掩盖的计算通信组合；
6. 通信能否与依赖无关的计算安全 overlap。

通信方案必须结合 [communication-overlap.md](references/communication-overlap.md) 建立依赖 DAG、字节量和关键路径证据，不能只根据 API 名称判断。

基础阶段还要检查算法复杂度、算子发射碎片、Layout/dtype 往返转换、临时内存、重复分配、Shape 分支、Graph Capture 稳定性、PREFILL/DECODE 差异和缓存失效规则。发现 Graph、调度、Host 空泡或 MLU 资源问题时读取 [运行时与 Graph 补充分析](references/runtime-optimization.md)。对每项候选估算可消除的 FLOPs、字节、Kernel 发射、Collective 字节或暴露通信时间，并按“收益上界、证据强度、风险、实施成本”排序。

先输出基础分析结论和可执行步骤。若获准修改，则从最高优先级候选开始实施、验证和接受/回退；完成所有已授权的基础改动后更新结论。`deep_analysis=false` 时在这里停止，不继续采集深层算子数据或提出 Triton 实现。

## 深度阶段：仅按条件执行

只有 `deep_analysis=true`，且基础分析以及获准的基础改动已经完成，才读取并执行 [deep-analysis.md](references/deep-analysis.md)。

深度阶段先探测当前会话可用能力，不把可选能力作为本 Skill 的运行依赖：

1. 性能数据优先使用已安装且可调用的 `xllm-performance-analysis`；不可用时选择能力匹配的性能分析 Skill；仍不可用时使用仓库已有 benchmark、Profiler、CNPerf/CNPX 或当前环境可用工具完成等价采集。不得伪造未获得的数据。
2. 当证据证明连续小算子、发射开销或中间结果访存值得融合时，优先使用已安装且可调用的 `xllm-triton-kernel-dev`；不可用时选择能力匹配的 Triton 实现与优化 Skill；仍不可用时按当前 xLLM Triton JIT 接口和正常开发流程实现与验证。
3. 使用可选 Skill 前必须完整读取其说明并遵循其更严格的正确性、性能和构建闸口。缺失时记录降级路径，不安装、不复制其内部实现，也不声称执行过对应流程。

基于导出的性能数据把算子映射回源码，分析连续小算子是否能被更高效算法、已有融合算子或 Triton Kernel 替代；对耗时较大的小算子检查上下文语义，比较等效算子、代数重写、批量化、融合、Layout 保持和重计算/物化权衡。

任何深度方案实施前都要做第二次审查：重新核对完整 Shape、dtype、Layout、量化、PREFILL/DECODE、Graph、并行拓扑、所有 Rank、边界输入和状态语义。允许局部专用优化，但必须为其他既有场景保留等价实现或明确 dispatch，修改前后的支持范围必须一致。

## 接受改动

每个候选都从当前最佳版本开始，并满足：

- 全部相关正确性测试、状态/别名检查和支持矩阵通过；
- 构建产物确实来自当前源码，相关 xLLM 设备构建通过；
- 在冻结工作负载上与当前最佳版本公平比较，收益超过测量噪声；
- 通信改动验证所有 Rank、Stream/Event 顺序、无死锁和数值一致性；
- 保护指标、内存和非目标场景没有不可接受回退。

失败、收益不确定或支持范围收窄时回退当前候选并保留证据。没有真实的同条件前后数据时，不宣称性能提升。

## 输出

使用 [report-template.md](references/report-template.md) 输出：范围和基线、调用链摘要、逐项分析证据、结论、优先级、已接受/拒绝改动、正确性和性能结果、剩余风险，以及按依赖排序的后续优化步骤。明确标注本次是否触发深度阶段以及可选能力的实际可用状态。
