# 深度分析流程

## 进入条件

只有主流程已将 `deep_analysis` 判定为 true，且基础分析产物已经完成，才能进入本阶段。若用户同时授权改动，先完成并验证已选定的基础改动，再以当前最佳版本作为深度分析基线；若用户只授权分析，则在基础分析报告完成后继续只读深挖。

## 探测可选能力

以当前会话明确提供的可用 Skill 清单为准；不要仅凭某个同名目录存在就声称已安装或已调用。选择可选 Skill 后必须由主执行者完整读取其 `SKILL.md` 及本次任务需要的引用资料。

性能分析路由：

1. 精确名称 `xllm-performance-analysis` 可用时优先选择。
2. 否则在可用清单中选择描述明确覆盖 xLLM、CNPerf/CNPX、模型/模块级性能采集和结构化导出的能力。
3. 若没有匹配能力，检查当前环境已有的 xLLM benchmark、Profiler、`cnperf-cli` 或 `cnpx`，使用可复现的最小流程采集；不得为了完成分析擅自安装工具。

Triton 路由：

1. 精确名称 `xllm-triton-kernel-dev` 可用时优先选择。
2. 否则选择描述明确覆盖当前设备、xLLM Triton 格式、正确性和多轮优化闸口的能力。
3. 若没有匹配能力，直接查阅当前 xLLM 的 Triton JIT 实现和相邻算子，按正常 Kernel 开发、精度验证、性能迭代和集成流程执行。

可选能力不可用不是分析结论。记录实际采用的降级路径和证据缺口，继续完成安全可行的工作。

## 性能数据采集

冻结与基础阶段相同的模型、阶段、Shape、并发、序列长度、dtype/量化、并行拓扑、预热和统计协议。采集范围要能区分 PREFILL 与 DECODE，并覆盖目标调用路径的稳定迭代。

优先保存结构化原始产物和可复现命令。若选中的性能分析能力支持 `.csv`、`.json` 和 `.cnperf-rep`，按其流程导出；只把实际成功生成且可读取的格式写入报告。记录：

- 端到端 TTFT、TPOT/ITL、时延或吞吐基线；
- 算子名称、次数、总耗时、单次耗时、占比和时间线位置；
- memcpy、同步、Collective、Host 空泡和并发关系；
- 设备、软件环境、采集命令、数据文件和源码版本。

Profiler 会扰动执行，算子耗时之和也可能因并发而大于端到端时间。用 profile 定位和解释，用同条件端到端 benchmark 决定接受或回退。

## 从性能数据回到代码

将热点算子和时间线片段映射到准确的模型、Layer、函数和调用行，补充实际 Shape、执行频次和消费者。重点检查：

- 连续小算子是否表达一个可用代数重写、批量操作或已有融合算子完成的整体语义；
- 中间 Tensor 是否只服务相邻算子，是否可在一次 Kernel 内保留和消费；
- 小算子串是否由 Python/C++ 循环、反复 cast/Layout 或标量读取人为产生；
- 高耗时小算子是否在上下文中计算了不需要的完整结果；
- 高耗时算子能否使用等效原生算子、不同分解、批量 API、融合 epilogue 或专用 Kernel；
- 新方案是否减少端到端关键路径，而不只是把一个算子的时间转移到另一个名字。

## Triton 候选判定

只有满足以下条件才提出 Triton 实现：

- 目标是稳定且可测量的设备热点，小算子发射或中间访存成本不可忽略；
- 语义和边界可以由当前 xLLM Triton JIT ABI 表达；
- 有可信 Reference 和覆盖完整支持矩阵的 Case；
- 融合边界不跨越非法全局同步、不可控副作用或不安全别名；
- 相比已有原生/融合算子，预期收益足以覆盖开发和维护成本。

优先顺序通常是：删除工作 -> 代数或批量替代 -> 复用已有高效算子 -> 融合已有路径 -> 新建 Triton Kernel。不能因为能够写 Triton 就默认它是最佳方案。

## 实施前第二次检查

在任何深度改动前，形成“提议方案—现有语义—支持矩阵”对照并重新搜索全部调用者。至少确认：

- PREFILL、DECODE、Chunked Prefill 和零 Token/空 Batch 等相关阶段；
- 所有既有 Shape、动态维度、非对齐尾块、dtype、量化和 Layout；
- 单卡以及 TP/PP/EP/DP 组合、所有参与 Rank；
- optional 参数、in-place、别名、cache、随机性和状态更新；
- Graph Capture/Replay、JIT Specialization、Stream 和通信顺序；
- 非目标硬件或配置的 dispatch/fallback 行为。

局部特化必须使用显式、可测试的 dispatch。非命中场景继续走语义等价路径；不得删除原先支持的场景、放宽精度标准或让失败静默降级。

## 深度迭代

每轮只实现一个可证伪假设，从当前最佳版本开始。先运行支持矩阵正确性，再做冻结 benchmark；需要解释算子变化时重新采集同协议 profile。接受后把新版本设为当前最佳，失败或收益处于噪声范围则回退当前候选并保留证据。

使用 Triton 能力时，遵守其要求的优化轮数、证据和接入闸口；当前 Skill 不降低更严格的要求。完成后重新验证实际模型调用链，而不只验证裸 Kernel。
